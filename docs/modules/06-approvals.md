# الجزء 06: محرك الموافقات — المواصفة

> المرحلة 0 من [خط الإنتاج](../MODULE-PIPELINE.md). الحالة: **مُسلَّم**.
> يعتمد على: [الجزء 04](04-projects.md) و[05](05-work-items.md) و[05b](05b-relations-comments.md) (مُسلَّمين).
> المرجع (للفهم فقط): `ipm-web/src/app/domain/approvals/{approval.models,approval.api}.ts`، `mock/server/handlers/approvals.handlers.ts`، `mock/server/approvals/engine.ts`،

## 1. الهدف
محرك الموافقات هو اللي بيحوّل الانتقالات المعلَّمة `requiresApproval` (بالمشاريع 04 وعناصر العمل 05) من «تجاوز بصلاحية `audit.override`» لـ **طلب موافقة حقيقي**: قوالب بمراحل متسلسلة، طلبات، قرارات، تفويض، وربط بالانتقال.
بيشمل: القوالب وقواعد انطباقها، تقديم الطلب، المعتمدون (مستخدم أو دور أو منصب) بتجميدهم عند التقديم، القرار (موافقة أو رفض أو إرجاع) مع منع اعتماد الذات، إعادة التقديم، الموافقة الجماعية، التذكير، التفويض المؤقت، البوابة اللي بتفتح الانتقال مرة وحدة خلال مهلة، وإبطال الطلب المعلّق إذا تغيّر حقل محمي.

> **تقسيم:** التعديل الحساس (`sensitive.change`: قيم مقترحة بتنطبّق ذرّياً بعد الاعتماد، ومنع التعديل المباشر للحقول المحمية) بجزء لحاله، **06b**، لأنه بيمسّ كل أوامر التعديل (مشروع، عنصر، أب، نوع، مسؤولون…). هون القوالب بتقبل الحدث `sensitive-change` (تخزيناً وتحققاً) لكن الطلبات منه ما بتتقدّم لحد 06b.

## 2. الجداول (schema `approvals`)
| الجدول | الأعمدة | القيود |
|---|---|---|
| `approval_templates` | `id`، `name`، `event`، `is_active`، **`stages jsonb`** (`[{ order, name, approverKind, approverId, dueHours? }]`)، **`protected_fields text[]`**، **`rule jsonb`** (كائن واحد، اختياري)، `allow_self_approval` + الأختام + `xmin` | `name` 1–150؛ `event` من `project-approve` `project-close` `work-item-approve` `sensitive-change` (CHECK)؛ لا حذف (تعطيل فقط) |
| `approval_requests` | `id`، `template_id`، `subject_type` (`project`/`work-item`)، `subject_id`، `project_id`، `title`، `requester_id`، `status`، `current_stage`، `revision`، **`snapshot jsonb`** (`{ field: value }`)، **`decisions jsonb`**، **`stages jsonb`** (نسخة مجمّدة من القالب)، **`resolved_approvers jsonb`** (`[{ order, userIds }]`)، `action`، `target_status_id`، `stage_due_at`، `last_reminded_at`، `consumed_at` + الأختام + `xmin` | `status` من `pending-approval` `approved` `rejected` `returned` `superseded` (CHECK)؛ `action` من `close` `reopen` `activate`؛ FK للقالب والمشروع والمقدِّم؛ فهرس `(subject_type, subject_id, status)` و`(project_id, status)` |
| `delegations` | `id`، `from_user_id`، `to_user_id`، `from_date`، `to_date`، `reason`، `is_active` + الأختام + `xmin` | `to_date ≥ from_date` (CHECK)؛ FK للمستخدمين؛ فهرس `(from_user_id, is_active)` و`to_user_id` |

- القرارات والمراحل المجمّدة والمعتمدون المحلولون **أعمدة بالطلب نفسه** (jsonb): كل قرار بيحرّك `xmin` (ETag) وبيظهر بـ `audit_log` كاملاً. ما في جدول قرارات منفصل.
- **الطلب بيحتفظ بنسخة مجمّدة من مراحل القالب** وقت التقديم: تعديل القالب بعدها ما بيمسّ الطلبات الجارية.
- **الاستهلاك:** `consumed_at` بيتعبّى لما الموافقة تنصرف بانتقال (استعمال واحد، R9).
- الـ enums بالنص kebab-case (`pending-approval`، `project-approve`، `work-item`، القرار `approve`/`reject`/`return`، نوع المعتمد `user`/`role`/`position`، المنصب `project-owner`/`direct-manager`/`project-manager`).

## 3. الصلاحيات
الفحص **بالمعالج** (بالمشروع) متل 04: مشروع غير مرئي ← **404**، مرئي بدون الصلاحية ← **403** (ويتسجّل `permission-denied`).
| الصلاحية | نطاقها | بتفتح |
|---|---|---|
| `approvals.request` | مشروع | تقديم طلب موافقة (وإعادة التقديم) |
| `approvals.view` | مشروع | رؤية كل طلبات المشروع (غيرها: المقدِّم والمعتمد الحالي) |
| `approvals.decide` | مشروع | اتخاذ قرار (ولازم تكون معتمد المرحلة الحالية أو مفوَّضاً) |
| `approvals.configure` | نظام | إدارة القوالب، وإدارة تفويضات غيرك، والتذكير بأي طلب |
| `audit.override` | نظام | يبقى مخرج طوارئ للانتقال بدون موافقة (R9)، ويتسجّل |

القوالب تنقرأ لأي مسجّل (لازم لشاشة التقديم والمطابقة)، والكتابة بـ`approvals.configure`.

## 4. قواعد العمل
| # | القاعدة | الخطأ |
|---|---|---|
| R1 | **القالب:** الاسم مطلوب، `event` معروف، مراحل بترتيب متسلسل فريد من 1، كل مرحلة باسم و`dueHours` (1–720 اختياري)، المعتمد: مستخدم **نشط موجود** أو دور موجود (نظام أو مشروع) أو منصب صالح، ولا يتكرر نفس المعتمد بمرحلتين متتاليتين. `protectedFields` من حقول نوع الموضوع (مشروع: `name description startDate endDate ownerId members`؛ عنصر: `title description dueDate startDate parentId priority typeId assigneeIds relations`). القالب المعطّل ما بيتحقق منه. لا حذف، تعطيل فقط | 400 (حقل) `ApprovalTemplate.Invalid` |
| R2 | **القاعدة (`rule`):** `workItemTypeIds` `projectIds` `priorities` `actions` (`close` `reopen` `change` `activate`) `conditions` (`eq` `neq` `gt` `lt` `in` على حقول الموضوع) و`priority` (عدد صحيح). كلها اختيارية، والغائب = ينطبق على الكل | 400 |
| R3 | **المطابقة** (`GET /approval-templates/match`): من القوالب الفعّالة اللي بتحكم الموضوع والإجراء: الأعلى `rule.priority`، ثم الأكثر تحديداً (عدد العناصر المحددة بالقاعدة)، ثم الأقدم. فاضي = `null` | 400 إذا الإجراء غير معروف |
| R4 | **التقديم** (`POST /approvals`): الموضوع مرئي و`approvals.request` بمشروعه، **المشروع غير مؤرشف**، القالب فعّال وبينطبق على الموضوع بقاعدته (وإلا 422)، حدث القالب بيتوافق مع الإجراء (`close` أو `reopen` أو `activate`؛ والمُستنتج: مشروع+`project-close` ← `close`، مشروع غيره ← `activate`، عنصر بحالة منجزة/ملغاة ← `reopen` وغيره ← `close`)، ما في طلب معلّق لنفس الموضوع والقالب (409)، وكل مرحلة إلها معتمد واحد على الأقل (422 `Approval.StageUnresolvable`). بيتحفظ `snapshot` للحقول المحمية، وتتجمّد مراحل القالب والمعتمدون، وبتبدأ المرحلة 1 | 404 / 403 / 409 `Approval.AlreadyPending` / 422 |
| R5 | **المعتمدون:** مستخدم بعينه؛ دور = أعضاء المشروع بهالدور + مستخدمو النظام اللي عندهم هالدور؛ منصب: مالك المشروع، المدير المباشر لمقدِّم الطلب، مدير المشروع (أعضاء بدور `project_manager`). **بيتحلّوا مرة وحدة عند التقديم** وبيتجمّدوا؛ **التفويض بيضل حياً** (R13) | — |
| R6 | **القرار** (`POST /approvals/{id}/decide`): `approvals.decide` بالمشروع، `revision` مطابق (وإلا 409 `Approval.Stale`، ولو الطلب `superseded` كمان)، الحالة `pending-approval`، المقدِّم ما بيقرّر على طلبه (403) **حتى يتوفر الإعداد العام بالجزء 09** (قيمة ثابتة «ممنوع»؛ عمود `allow_self_approval` بالقالب جاهز)، ولازم تكون من معتمدي المرحلة الحالية أو مفوَّضاً عن أحدهم (وإلا 403). الرفض والإرجاع **يتطلبان تعليقاً** (400). الموافقة بتنقل للمرحلة التالية أو `approved` إذا كانت الأخيرة. القرار بالتفويض بيسجّل `onBehalfOf` | 404 / 403 `Approval.NotApprover` / 403 `Approval.SelfDecision` / 409 / 422 `Approval.NotPending` / 400 |
| R7 | **الرفض والإرجاع:** `rejected` أو `returned` وبينتهي التقدّم (`current_stage = 0`). **إعادة التقديم** (`POST /approvals/{id}/resubmit`) للمقدِّم فقط وللطلب `returned` أو `superseded`: `revision + 1`، وبتبدأ من المرحلة 1 بلقطة ومعتمدين جدد، وكل المراحل لازم تنحلّ (R4) | 403 / 422 `Approval.NotResubmittable` |
| R8 | **الموافقة الجماعية** (`POST /approvals/bulk-decide`): موافقة فقط، من 1 إلى 50 طلباً، ولازم رقم `revision` لكل طلب (تأكيد إنك راجعت هالإصدار). النتيجة لكل طلب `{ id, ok, message }` والباقي ما بيوقف | 400 |
| R9 | **البوابة:** الانتقال المعلَّم `requiresApproval` (مشروع 04 أو عنصر 05) بيحتاج طلباً `approved` من الحدث المناسب، **غير مستهلك** و**لم يمضِ عليه 14 يوماً** من قراره، وإجراؤه وحالته الهدف يطابقوا الانتقال، وحقوله المحمية لم تتغيّر عن اللقطة. بعد نجاح الانتقال بيتعلّم `consumed_at` (استعمال واحد، بنفس المعاملة). **`audit.override` بيضل مخرجاً**: بدون طلب مناسب ومعه الصلاحية بينفّذ ويتسجّل `approvalOverridden` (متل 04 و05) | 422 `Project.ApprovalRequired` / `WorkItem.ApprovalRequired` |
| R10 | **تغيّر حقل محمي بعد الموافقة:** البوابة بترفض (422) وبيتسجّل `approval.gate_blocked` باسم الحقول، ويلزم طلب جديد | 422 `Approval.ProtectedFieldsChanged` |
| R11 | **الإبطال:** تغيير حقل محمي (بقالب الطلب) لموضوع طلبه `pending-approval` بيحوّل الطلب لـ`superseded` فوراً بنفس المعاملة (والطلب يعيد التقديم R7). الأوامر اللي بتشغّل الإبطال: تعديل المشروع (الاسم، التواريخ، المالك)، أعضاء المشروع، تعديل العنصر (العنوان، الوصف، الأولوية، التواريخ، المسؤولون، الأب)، تغيير النوع، وإنشاء/حذف الروابط (`relations`)، بما فيها التعديل الجماعي | — |
| R12 | **القراءة:** `GET /approvals?box=inbox|sent|closed` (الافتراضي `inbox`): `inbox` = اللي تقدر تقرّر عليها هلق، `sent` = اللي قدّمتها، `closed` = غير المعلّقة وإنت طرف فيها (مقدِّم أو قرّرت أو معك `approvals.view`). الفلاتر: `status` `projectId` `subjectType` `subjectId` `templateId` `overdue=true`، والترتيب `updatedAt` تنازلي. طلب بدون علاقة ولا `approvals.view` بالمشروع ← **404**. الرد بيزيد `overdue` و`canDecide` للمستخدم الحالي | — |

## 6. البيانات الأولية
- **دايماً:** قوالب الواجهة الثلاثة للموافقة: «اعتماد مشروع جديد» (مراحل: المسؤول المباشر، مدير المشروع، الاعتماد النهائي)، و«اعتماد إنجاز مهمة» (المشرف التقني ثم مدير المشروع، لأنواع المهمة والميزة والخطأ)، و«إغلاق مشروع». معتمدو المستخدمين بالاسم بتتحوّل لمعتمدين بمناصب/أدوار من النظام (المدير المباشر، دور `approver`، دور `project_manager`، ودور `system_admin` للاعتماد النهائي) لأن معرّفات المستخدمين ما بتنثبت.
- **بالتطوير فقط (`Seed:Demo`):** الطلبات التجريبية الأربعة من الواجهة (واحد على مشروع BI، وثلاثة على عناصر ERP/SSP بحالات معلّق ومعتمد ومرفوض) بقراراتها.
- قوالب `sensitive-change` التجريبية بتجي مع 06b.

## 7. سيناريوهات القبول
1. **القوالب:** `admin` (`approvals.configure`) بينشئ قالباً بمرحلتين ← 201؛ غير مسموح (`khaled`) ← 403؛ مراحل بترتيب مكسور أو معتمد غير موجود/غير نشط أو نفس المعتمد متتالياً أو `dueHours` خارج المدى ← 400 بمسار الحقل؛ أي مسجّل بيقرا ويطابق؛ تعديل بـ If-Match.
2. **المطابقة (R3):** قالبان لنفس الحدث: الأعلى `priority` بيربح، وعند التساوي الأكثر تحديداً، ثم الأقدم؛ بدون قالب ينطبق ← `null`.
3. **التقديم (R4):** `reem` (عضو فريق) بتقدّم إنجاز مهمة ← 201 بحالة `pending-approval` والمرحلة 1 ولقطة؛ قالب لا ينطبق بقاعدته ← 422؛ ثاني معلّق لنفس الموضوع ← 409؛ مرحلة بدون معتمد ← 422؛ مشروع مؤرشف ← 422؛ `abdullah` ← 403؛ خارج المشروع ← 404.
4. **المعتمدون (R5):** دور = أعضاء المشروع + أصحاب الدور بالنظام؛ منصب المدير المباشر والمالك ومدير المشروع؛ والتجميد: إزالة معتمد من المشروع بعد التقديم ما بتغيّر مين بيقرّر.
5. **القرار (R6):** المعتمد بيوافق ← تنتقل المرحلة؛ آخر موافقة ← `approved`؛ غير المعتمد ← 403؛ المقدِّم على طلبه ← 403؛ رفض/إرجاع بدون تعليق ← 400؛ `revision` قديم ← 409؛ طلب غير معلّق ← 422.
6. **الرفض والإرجاع وإعادة التقديم (R7):** الرفض بينهي؛ الإرجاع بيعيد التقديم للمقدِّم فقط فبيزيد الإصدار ويبدأ من المرحلة 1 بقرارات قديمة محفوظة؛ ومن غيره 403.
7. **الجماعي (R8):** موافقة على عدة طلبات مع أرقام إصداراتها: نتيجة لكل طلب، طلب بإصدار غلط لا يوقف الباقي؛ بدون `revisions` أو رفض جماعي أو أكتر من 50 ← 400.
8. **البوابة بالمشروع (R9):** انتقال المشروع `pending ← active` بدون موافقة ← 422 (للي معه `audit.override` ينفّذ بالتجاوز وبيتسجّل)، وبعد طلب معتمد ← 200 وبيتعلّم `consumed_at`؛ استعماله مرة ثانية ← 422؛ بعد 14 يوماً ← 422؛ طلب لإجراء أو حالة مستهدفة ثانية ← 422.
9. **البوابة بالعنصر:** نفس الشي لانتقال عنصر بشرط الموافقة (قالب ينطبق على نوعه)، ومنع الاستعمال لعنصر ثاني.
10. **الحقول المحمية (R10/R11):** بعد الموافقة وقبل الانتقال، تعديل حقل محمي ← الانتقال 422 `ProtectedFieldsChanged`؛ وتعديل حقل محمي والطلب معلّق ← `superseded` وإشعار لا يزال لـ08؛ وإعادة التقديم بتفتحه من جديد؛ وتعديل حقل غير محمي ما بيغيّر شي.
11. **التفويض (R13):** `khaled` بيفوّض `noura` فبتقدر تقرّر نيابة عنه خلال الفترة وبيظهر `onBehalfOf`؛ خارج الفترة أو ملغى ← 403؛ تفويض لنفسه أو لغير نشط أو لمن لا يملك القرار أو متداخل أو مدة > 90 يوماً أو بدون سبب ← 400/409؛ إلغاء بالمفوِّض أو `approvals.configure`.
12. **القراءة (R12):** `inbox` للمعتمد (و`canDecide`)، `sent` للمقدِّم، `closed` بعد القرار؛ طلب بدون علاقة ← 404؛ `overdue=true`.
13. **التذكير (R14):** المقدِّم يذكّر ← 200؛ مرتين بالساعة ← 429؛ غير المقدِّم ← 403؛ طلب غير معلّق ← 422.
14. **التأخّر (R15):** مرحلة بـ`dueHours` بتحسب `stageDueAt`؛ بعد الموعد `overdue = true`.
15. كل تعديل بيظهر بـ `audit_log` مع `user_id`؛ `dotnet test` ناجح؛ الروابط ظاهرة بـ `/docs`؛ و`docs/http/06-approvals.http` فيه مثال لكل رابط.

## 11. تعديلات أثناء التنفيذ
غيّرتها أثناء المراحل 1–4 بدون ما تغيّر الاتفاق، وكلها موثّقة هون:
1. **القالب المعطّل:** بنتحقق من بنيته (مراحل، ترتيب، منصب) دايماً، لكن وجود المعتمد/الدور والمشاريع والأنواع بالقاعدة بيتفحص للقالب **الفعّال فقط** (متل الـ mock). أخطاء القالب بمسارات مثل `stages[1].approverId` و`rule.projectIds`.
2. **مفاتيح الـ JSON:** `from` و`to` بالتفويض تواريخ `yyyy-MM-dd`؛ والقيم بصيغة kebab (`pending-approval`، `work-item`، `approve`). فلاتر `GET /approvals` (`status` و`subjectType`) بتاخد نفس النص، ولذلك بتتحقق بالـ validator (400 لقيمة غير معروفة).
3. **`GET /approval-templates/match`** بيرجّع `null` JSON صريح (200) إذا ما في قالب ينطبق، و404 إذا العنصر غير موجود أو مخفي.
4. **عدم الرؤية:** طلب خارج مشروعك أو بدون علاقة ولا `approvals.view` ← 404 `Approval.NotFound`. أما عضو بالمشروع معه `approvals.view` ويفتقر `approvals.decide` أو `approvals.request` فبيشوف 403 عند القرار أو التقديم.
5. **القرار:** يحتاج `If-Match` (ETag الطلب) **و** `revision` (الإصدار اللي راجعته)، وكلاهما مستقلان: ETag قديم ← 412، و`revision` قديم ← 409. الموافقة الجماعية بدون `If-Match` (متل التعديل الجماعي بـ05).
6. **التذكير:** الساعة بين تذكيرين مشتركة للطلب (مش لكل مستخدم)، فمدير الموافقات اللي بيذكّر بعد المقدّم خلال الساعة بياخد 429.
7. **البوابة:** `ApprovalGate` بتصرف الطلب بنفس `SaveChanges` الانتقال (ما بيضيع طلب ولا بينصرف مرتين). سجل `approval.gate_blocked` المقترح بالمواصفة تحوّل لخطأ `Approval.ProtectedFieldsChanged` فقط (التدقيق الكامل للحدث بالجزء 08).
8. **الإبطال (R11):** يمر عبر `ApprovalSupersession` قبل الحفظ بنفس المعاملة. المشغّلات: تعديل المشروع (الاسم والوصف والتواريخ والمالك)، الأعضاء، تعديل العنصر (العنوان والوصف والأولوية والتواريخ والمسؤولون)، الأب، النوع، الروابط (إنشاء/حذف)، والتعديل الجماعي.
9. **المعتمدون:** المستخدم غير النشط بيُستبعد وقت التجميد؛ مرحلة بدون أي معتمد نشط ← 422 `Approval.StageUnresolvable`. الدور بيشمل أعضاء المشروع بهالدور ومستخدمي النظام بهالدور.
10. **الـ seed:** معرّفات القوالب `…-8012-…` والطلبات `…-8013-…`. القوالب الافتراضية الثلاثة دايماً، ومعتمدو المراحل أدوار ومناصب (`approver` و`project_manager` و`system_admin` والمدير المباشر) بدل مستخدمين بالاسم. الطلبات الأربعة بالتطوير فقط، وكل قراراتها مسجّلة بالتواريخ النسبية.
11. **اختبار من الجزء 04:** «يشوف مشروعه بس» للقارئ `abdullah` صار يقارن المشاريع التجريبية فقط، لأن اختبارات الأجزاء الجديدة بتضيفه لمشاريعها هي.
