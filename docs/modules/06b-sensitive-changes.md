# الجزء 06b: التعديل الحساس — المواصفة

> المرحلة 0 من [خط الإنتاج](../MODULE-PIPELINE.md). الحالة: **مُسلَّم**.
> يعتمد على: [الجزء 06](06-approvals.md) (مُسلَّم)، وعلى [04](04-projects.md) و[05](05-work-items.md) و[05b](05b-relations-comments.md).
> المرجع (للفهم فقط): `ipm-web/src/app/mock/server/approvals/engine.ts` (`validateProposedChanges`، `applyProposedChanges`، `assertNoDirectSensitiveChange`، `changedSinceSnapshot`)،
> `mock/server/handlers/approvals.handlers.ts` (`decideRequest` عند آخر موافقة، `requireEditRights`)، `mock/db/seed.ts` (قالبا `sensitive.change`)، وSRS FR-APR-09/10.

## 1. الهدف
بعض الحقول لازم ما تتغيّر بقرار شخص واحد: عنوان مهمة حرجة، تاريخ استحقاقها، أبوها، أو اسم مشروع فعّال وتواريخه ومالكه. التعديل الحساس بيخلّي التغيير **طلب موافقة** بالقيم المقترحة، وما بيتطبّق إلا بعد موافقة آخر مرحلة، **ذرّياً** (كل الحقول مع بعض أو ولا واحد).
وبيسكّر الباب الثاني: لما يكون في قالب `sensitive-change` فعّال بيحكم العنصر، **التعديل المباشر** للحقل المحمي بيتمنع (422) وبيتوجّه للطلب.

## 2. الجداول
ما في جدول جديد. عمود واحد جديد بجدول الجزء 06:
| الجدول | العمود | ملاحظات |
|---|---|---|
| `approval_requests` | **`proposed_changes jsonb`** (`[{ field, value }]`، فاضي لغير التعديل الحساس) | القيم نصوص: تواريخ `yyyy-MM-dd`، أولوية kebab، معرّفات GUID، والمسؤولون معرّفات مفصولة بفواصل ومرتّبة؛ `null` يعني «أزل القيمة». الطلب `approved` بيحتفظ بالقيم المطبَّقة كسجل |

- بيتحرّك الـ ETag مع كل تعديل ويظهر بـ `audit_log`. فعل التطبيق نفسه بيظهر بسجل العنصر/المشروع بمستخدم **آخر معتمد**.
- لقطة الحقول المحمية (`snapshot`) بتتجدّد بعد التطبيق لتعكس القيم الجديدة.

## 3. الصلاحيات
| الفعل | الصلاحية |
|---|---|
| تقديم طلب تعديل حساس | `approvals.request` بالمشروع **و** صلاحية التعديل المباشر لكل حقل مقترح (R3) |
| القرار | `approvals.decide` + معتمد المرحلة (مثل 06) |
| تجاوز المنع المباشر (R9) | `audit.override` (نظام) |

صلاحية التعديل المباشر لكل حقل: المشروع (`name description startDate endDate`) ← `projects.edit`، `ownerId` ← `projects.edit`؛ العنصر: `assigneeIds` ← `tasks.assign`، `typeId` ← `workitem.types.manage`، وغيرها ← `tasks.edit`.

| R12 | **القوالب:** إنشاء قالب `sensitive-change` (06 R1) بيتطلب حقولاً محمية من نوع موضوع واحد، ولا بيقبل `members` أو `relations` كحقل مقترح (بيقبلها كحقل مراقَب للإبطال فقط) | 400 |

## 5. الروابط
ما في روابط جديدة. بتتغيّر:
| الرابط | التغيير |
|---|---|
| `POST /approvals` | بيقبل `proposedChanges` (للقوالب `sensitive-change` فقط، وغيرها بيرجع 422 `Approval.ProposedChangesNotAllowed`)، وبيرد 201 بالطلب (الإجراء `change`) |
| `POST /approvals/{id}/decide` | عند موافقة آخر مرحلة على طلب حساس بيطبّق R6، وبيرجع الطلب `approved` |
| `POST /approvals/{id}/resubmit` | R10 |
| `PUT /projects/{id}` · `PUT /work-items/{id}` · `PUT /work-items/{id}/parent` · `POST /work-items/{id}/type-change` · `POST /work-items/bulk` | R8: 422 `Approval.ChangeRequiresApproval` |
| `GET /approvals` · `GET /approvals/{id}` | حقل `proposedChanges` |

أخطاء جديدة: `Approval.SubjectArchived` (422)، `Approval.FieldsNotProtected` (422)، `Approval.NoChange` (422)، `Approval.ProposedChangesNotAllowed` (422)، `Approval.ChangeRequiresApproval` (422)؛ أخطاء R4 بصيغة التحقق 400.

## 6. البيانات الأولية
- **بالتطوير فقط (`Seed:Demo`):** قالبا الواجهة:
  - «تعديل حساس على مهمة حرجة»: حدث `sensitive-change`، حقول محمية `title dueDate parentId priority`، قاعدة (نوع «مهمة»، أولوية `critical`، إجراء `change`، أولوية 10)، مرحلة واحدة «مدير المشروع» (دور `project_manager`، مهلة 48 ساعة).
  - «تعديل حساس على مشروع فعّال»: حقول محمية `name startDate endDate ownerId`، قاعدة (إجراء `change`، وشرط `statusId = نشط`)، مرحلة واحدة «الاعتماد النهائي» (دور `system_admin`).
- **ما بنزرعهم دايماً** (عكس قوالب 06 الثلاثة) لأن وجودهم بيمنع التعديل المباشر على أي تثبيت جديد؛ المدير بينشئهم لما يحتاجهم.

## 7. سيناريوهات القبول
1. **التقديم (R1):** `reem` (عضو فريق) بتقدّم تعديلاً لعنوان وتاريخ استحقاق مهمة حرجة بقالب بقاعدتها ← 201 بحالة `pending-approval` والإجراء `change` و`proposedChanges` و`snapshot` للحقول المحمية؛ قالب غير حساس مع `proposedChanges` ← 422؛ بدونها ← 422؛ عنصر مؤرشف أو مشروع مؤرشف ← 422.
2. **الانطباق (R2):** حقل خارج `protectedFields` أو `members`/`relations` ← 422 `FieldsNotProtected`؛ مهمة لا تنطبق عليها القاعدة (أولوية ليست حرجة) ← 422 `TemplateNotApplicable`.
3. **صلاحية الطالب (R3):** `abdullah` (قارئ) ← 403؛ عضو بدون `tasks.assign` يقترح مسؤولين ← 403.
4. **صحة القيم (R4):** عنوان فاضي، أولوية غلط، تاريخ استحقاق قبل البداية، مسؤول غير عضو أو غير نشط، أب من مشروع ثاني أو بنوع غير مسموح أو يسبب حلقة، نوع فيه تعارضات ← 400 بمسار الحقل.
5. **لا تغيير (R5):** إرسال القيم الحالية نفسها ← 422 `NoChange`.
6. **التطبيق الذرّي (R6):** موافقة المرحلة الأخيرة بتغيّر كل الحقول المقترحة معاً، والطلب `approved` و`consumedAt`، واللقطة بالقيم الجديدة، وأثر `audit_log` بالمعتمد؛ موافقة مرحلة وسطى ما بتطبّق شي.
7. **الانجراف (R6-ب):** تغيير حقل محمي بالمسار المسموح (`audit.override`) بعد التقديم وقبل آخر موافقة ← الطلب أصلاً `superseded` (R7 بـ06)؛ ولو تغيّر بعد ما صار بالمرحلة الأخيرة بلا إبطال (حقل غير مراقَب) ← القرار 409 ولا يتطبّق شي.
8. **فشل التطبيق (R6-ج/د):** الأب المقترح صار مؤرشفاً قبل الموافقة، أو الطالب فقد صلاحيته ← القرار يفشل ويضل الطلب معلّقاً بمرحلته.
9. **المنع المباشر (R8):** `khaled` (مدير المشروع) بيعدّل عنوان المهمة الحرجة مباشرة ← 422 `ChangeRequiresApproval` باسم القالب والحقل؛ وتعديل حقل غير محمي (الوصف) ← 200؛ وإرسال نفس العنوان ← 200؛ وبالمشروع الفعّال: الاسم/التواريخ/المالك مباشرة ← 422، والوصف ← 200؛ والتعديل الجماعي لأولوية عنصر حرج ← فشل ذاك العنصر فقط.
10. **تغيير الأب والنوع (R8):** كلاهما بيرجع 422 للعنصر المحكوم، و200 لعنصر لا تحكمه القاعدة.
11. **المخرج (R9):** مدير النظام (`audit.override`) بيعدّل مباشرة ← 200؛ تعديل الأعضاء أو الروابط ما بيتمنع لكن بيبطل طلباً معلّقاً.
12. **بعد التطبيق (R7):** طلب آخر معلّق يحمي نفس الحقل ← `superseded`؛ وإعادة تقديمه تفحص القيم الجديدة (R10) فتفشل إذا صارت بدون تغيير.
13. **القراءة (R11):** `GET /approvals/{id}` بيرجّع `proposedChanges`، وقبل التطبيق القيم الحالية بالعنصر لم تتغيّر.
14. كل تعديل بيظهر بـ `audit_log` مع `user_id`؛ `dotnet test` ناجح؛ الروابط المتغيّرة موصوفة بـ `/docs`؛ و`docs/http/06b-sensitive-changes.http` فيه مثال لكل حالة.

## 8. قرارات
**حسمها صاحب المشروع:** تقسيم 06 على 06 و06b (موافقة الجزء 06).

**أخدتها أنا (صحّحني إذا لازم):**
- **`audit.override` بيتجاوز المنع المباشر** متل ما بيتجاوز البوابة بـ06، والتدقيق بيسجّل المستخدم. إذا بدك المنع مطلقاً بدون أي تجاوز قلّي.
- **القوالب الحساسة بتنزرع بالتطوير فقط** (مش دايماً)، لأن منعها للتعديل المباشر بيغيّر سلوك أي تثبيت جديد. معناه إن اختبارات التكامل (اللي بتشتغل بـ`Seed:Demo`) رح تتأثر بعمل مشاريع/عناصر تطابق قاعدتها، وبعدّل اللي بيتأثر منها.
- **الأعضاء والعلاقات ما بتُقترح ولا بتُمنع مباشرة:** بتراقَب بالإبطال فقط (كما بالـ mock).
- **التطبيق عند آخر موافقة بنفس معاملة القرار:** فشله بيفشّل القرار ويترك الطلب معلّقاً بمرحلته، بدل ما يصير `approved` وما يتطبّق.
- **القيم المقترحة نصوص** بنفس صيغة اللقطة (للمقارنة المباشرة)، والمسؤولون مفصولين بفواصل ومرتّبين؛ أما رد العنصر فبيضل بشكله العادي.
- **المنع المباشر بيقارن القيم المتغيّرة فعلاً**، فإرسال العنصر كامل مع تغيير حقل غير محمي ما بيُمنع.
- **رسالة المنع نصية** (باسم القالب والحقول بالرسالة) لأن صيغة الخطأ ما بتحمل حقولاً إضافية؛ الواجهة بتعتمد على الرمز.
- **الإشعارات** (طلب بانتظارك، تم التطبيق) بالجزء 08.

## 11. تعديلات أثناء التنفيذ
غيّرتها أثناء المراحل 1–4 بدون ما تغيّر الاتفاق، وكلها موثّقة هون:
1. **التطبيق قبل تسجيل القرار الأخير:** `SensitiveChanges.ApplyAsync` بتشتغل **قبل** `request.Decide` بنفس الدالة المشتركة للقرار الفردي والجماعي، وبتتحقق من كل شي قبل ما تغيّر أي كيان. هيك فشل التطبيق ما بيترك الطلب أو العنصر متغيّراً بالذاكرة (مهم بالموافقة الجماعية اللي بتحفظ عنصراً عنصراً).
2. **أخطاء R6 بالتطبيق:** مشروع/عنصر مؤرشف ← 422 (`Approval.ProjectArchived` و`Approval.SubjectArchived`)، انجراف الحقول المحمية ← **409** `Approval.ProtectedFieldsChanged`، قيمة صارت غير صالحة ← 400 `Approval.ProposedChangesInvalid` (الرسالة بتجمع المشاكل)، الطالب فقد صلاحيته ← 403 `Approval.RequesterNotAllowed`. بالتقديم (R4) الأخطاء بمسارات الحقول `proposedChanges.<field>`.
3. **إعادة التقديم (R10):** بترمي 400 بمسارات الحقول أو 403 أو 422 `NoChange`، وبتترك الطلب مُعاداً كما كان.
4. **المنع المباشر (R8):** `SensitiveChangeGuard` بيشتغل قبل الحفظ بكل المشغّلات: تعديل المشروع والعنصر والأب والنوع والتعديل الجماعي (فشل ذاك العنصر فقط بنتيجة الجماعي). القالب الحاكم هو الأعلى `rule.priority` ثم الأقدم، ورسالة الخطأ بتسمّي القالب والحقول. حامل `audit.override` بيتجاوز.
5. **إبطال الطلب نفسه:** عند التطبيق الطلبات المعلّقة **الأخرى** اللي بتحمي نفس الحقول بتنبطل (R7)، والطلب المطبَّق ما بينبطل (استثناء `except`).
6. **القيم والمقارنة:** القيم بتتطبّع قبل الحفظ (أولوية صغيرة، معرّفات GUID بالصيغة القياسية، مسؤولون مرتّبون). مقارنة «بدون تغيير» بتعتبر الفاضي والـ null سواء.
7. **المهام الحرجة:** القالب التجريبي بيحكم مهام بنوع «مهمة» وأولوية `critical` فقط؛ والمشروع الفعّال بيحكمه شرط `statusId` بالحالة «نشط».
8. **الـ seed:** القالبان بمعرّفات `…-8012-…` (الرقمان 4 و5) وبالتطوير فقط.
9. **اختبار من الجزء 04:** «القارئ يقرا ولا يعدّل والمدير يعدّل» صار المدير يعدّل حقلاً غير محمي (يرسل الاسم والتواريخ الحالية) لأن ERP مشروع فعّال وتحكمه القاعدة الحساسة.
10. **التطبيق على مشروع:** `ownerId` بيتطبّق بعد الاسم والتواريخ، ويحتاج عضواً نشطاً (يتحقق عند التقديم وعند التطبيق).
